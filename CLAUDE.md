# Payments API — правила работы

API платежей для онлайн-школы: тарифы, создание платежа с промокодом и рассрочкой, `Idempotency-Key`,
вебхук банка со статусами. Python 3.11+, FastAPI, Pydantic v2, SQLAlchemy 2.x (sync, API в стиле 2.0), SQLite
(Postgres — опционально), pytest + httpx, ruff.

## Порядок работы

- Работаем **по одной фиче за раз**. Следующую фичу начинаем только по явной команде пользователя.
- Источник требований — ТЗ. Если по ходу работы решение расходится с ТЗ или ТЗ молчит — сначала
  согласовать с пользователем, потом код.
- После группы связанных фич — финальное ревью всего диапазона (шаг 4 цикла, от `main` перед первым
  слиянием группы до текущего `main`).

## Границы изменений — главное правило

Делаю только то, о чём попросили: минимальные изменения строго в рамках текущей фичи.

**Не получается реализовать фичу — не лезу в другие.** Если фича упирается в код другой фичи, общий модуль
или чужой тест, я **останавливаюсь и спрашиваю**, а не «дотолкиваю» её правками чужого кода. Объясняю, что
мешает, что предлагаю изменить и что может сломаться. Запрещено, чтобы «заработало»:

- менять код или тесты другой фичи;
- ослаблять, пропускать (`@pytest.mark.skip`, `xfail`) или удалять существующие тесты;
- обходить проверки (`--no-verify`, `# noqa`, `# type: ignore`, расширение `ignore` в ruff) без согласования.

Если упал тест другой фичи, значит я её сломал. Откатываю или исправляю своё изменение, а не чужой тест.

Остальные границы:

- Меняю только файлы и функции, нужные для текущей задачи. Не рефакторю, не переименовываю, не «улучшаю»
  и не форматирую код вне задачи.
- **Особо осторожно с общим**: `app/db.py`, `app/config.py`, `app/main.py`, `app/models.py`,
  `tests/conftest.py`, `pyproject.toml`, `requirements*.txt` — от них зависят все фичи. Не трогаю без
  согласия. Согласием считается одобренный план фичи (шаг 0 цикла).
- **Схема БД**: любая правка `app/models.py` (колонки, ограничения, типы) — отдельное согласование.
  Если подключён Alembic, изменение схемы идёт вместе с новой миграцией; слитые в `main` миграции не
  правятся задним числом.
- Код, который кажется неиспользуемым, не удаляю, не спросив.
- Заметил проблему вне задачи — не исправляю, а упоминаю в конце отчёта: «Заметил в X такую-то проблему —
  хочешь, займёмся отдельно?»
- Сомневаюсь, входит ли что-то в задачу, — считаю, что не входит, и спрашиваю.

## Цикл одной фичи

0. **План и согласование.** Кратко пишу, какие файлы изменю и что в каждом сделаю, отдельно отмечаю общие
   модули, схему БД, конфиги и зависимости, если их нужно тронуть. Начинаю только после «ок».
1. **Ветка фичи** от свежего `main`: `git switch -c feat/<slug>` (например `feat/installment-schedule`).
   Для исправлений — `fix/<slug>`.
2. **Реализация по TDD** (см. ниже). Каждое логическое изменение — отдельный коммит по шагу 3.
3. **Коммиты — строго по скиллу [`.agents/skills/git-commit/SKILL.md`](.agents/skills/git-commit/SKILL.md)**:
   анализ диффа → осознанный staging конкретных файлов (**без `git add -A` и `git add .`**) →
   Conventional Commit (тип, scope, описание в повелительном наклонении, строчная буква, без точки,
   заголовок < 72 символов). Перед коммитом проверки из раздела «Команды» зелёные, после — `git push`
   ветки (первый раз `git push -u origin <ветка>`).
4. **Код-ревью — строго по скиллу
   [`.agents/skills/requesting-code-review/SKILL.md`](.agents/skills/requesting-code-review/SKILL.md)**:
   запускается субагент `general-purpose` с промптом из
   [`code-reviewer.md`](.agents/skills/requesting-code-review/code-reviewer.md). Подставляются: описание
   сделанного, требования (описание фичи и относящиеся к ней правила ТЗ),
   `BASE_SHA = git merge-base main HEAD` и `HEAD_SHA = git rev-parse HEAD`. Обязательно после **каждой**
   фичи, даже если изменение «простое».
5. **Отчёт о реализации + Pull Request.** Открываю PR в `main`:
   `gh pr create --base main --title "<Conventional Commit заголовок>" --body-file <файл в scratchpad>`.
   Описание PR — **подробное**, на русском, по шаблону:
   - **Что сделано** — суть фичи; **каждый изменённый файл — одной строкой, что в нём изменено**; коммиты.
   - **Как работает** — поток данных (router → service → БД), ключевые решения, отклонения от ТЗ и почему.
   - **Что может зависеть** — какой код и какие фичи используют изменённое, что стоит перепроверить.
     Отдельно: изменения схемы БД, контрактов эндпоинтов, общих фикстур.
   - **Тесты** — какие добавлены (unit / API), результат прогона.
   - **Ручная проверка** — что лучше проверить только пользователю: пошаговые действия (curl) и ожидаемый
     результат. Если не нужна — так и написать.
   - **Ревью** — итог по уровням (шаг 6) и что решено исправить / отложить (дописывается после согласования).
   - В конце — строка атрибуции Claude Code.

   Пользователю в чат — тот же отчёт кратко + ссылка на PR.

6. **Отчёт по ревью** — проблемы по уровням, для каждой: `файл:строка`, суть, почему важно, как исправить:
   - 🔴 **Критичные** · 🟡 **Средние** · ⚪ **Мелочи**;
   - отдельно — что ревьюер счёл вне рамок требований («Declined to judge») и где я с ревьюером не согласен
     (с аргументами).
7. **Согласование.** Вопреки пункту «Fix Critical issues immediately» из скилла — **ничего не исправляю до
   ответа пользователя**, даже критичное. Предлагаю, что исправить сейчас, что отложить, и жду решения.
8. **Исправления** согласованных пунктов — в той же ветке, по тому же TDD, коммиты по шагу 3. Описание PR
   обновляю (`gh pr edit <N> --body-file ...`): раздел «Ревью» — что исправлено какими коммитами и что
   отложено.
9. **Слияние PR — делаю сам**, пользователь руками ничего не сливает. Условия: «ок» пользователя на
   исправления из шага 7 (или «исправлять нечего»), зелёные проверки на последнем коммите ветки (локально
   и в CI). Команды: `gh pr merge <N> --merge --delete-branch` → `git switch main && git pull` →
   проверки на `main`. Если на `main` что-то красное — сразу сообщаю и чиню через `fix/<slug>` по тому же
   циклу.
10. **Фича готова**, только когда: тесты зелёные, ревью пройдено, согласованные исправления сделаны, ветка
    слита в `main`, ручная проверка (если нужна) пройдена пользователем.

## TDD — обязательно

1. **Red:** сначала пишется тест, который падает по правильной причине (прогони его и убедись).
2. **Green:** минимальная реализация, чтобы тест прошёл.
3. **Refactor:** чистка при зелёных тестах.

Код без теста не коммитится. Исключения: чистый конфиг, миграции, документация.

## Виды тестов

| Вид   | Инструмент                         | Где                                 | Что проверяет                                                                      |
| ----- | ---------------------------------- | ----------------------------------- | ---------------------------------------------------------------------------------- |
| Unit  | pytest                             | `tests/test_pricing.py` и аналоги   | Чистые функции: промокод, скидка, график рассрочки, таблица переходов статусов     |
| API   | pytest + `TestClient` (httpx)      | `tests/test_<роутер>.py`            | HTTP-сценарии целиком: коды ответов, тела, и **состояние БД после запроса**        |

- Тест проверяет **результат, а не только код ответа**: суммы, `sum(schedule) == amount`, количество
  записей в БД, статус платежа после отказа в переходе (`GET` после 409).
- Каждый тест получает **своё приложение со свежей SQLite** в `tmp_path`: фикстура `client` собирает его
  через `create_app(database_url)`, фикстура `session` даёт сессию к той же базе для проверок. Тесты не
  зависят друг от друга и от порядка запуска, не трогают `payments.db` разработчика и не ходят в сеть.
- Однотипные случаи — через `@pytest.mark.parametrize` (3/6/12 месяцев, пары статусов), а не копипастой.
- Время в тестах не используется для логики; `created_at` проверяется только на наличие и формат.

## Команды

```bash
# окружение (Windows PowerShell: .venv\Scripts\activate; Linux/macOS: source .venv/bin/activate)
python -m venv .venv
pip install -r requirements-dev.txt

uvicorn app.main:app --reload           # запуск, Swagger на http://127.0.0.1:8000/docs

pytest                                  # все тесты
pytest tests/test_pricing.py -k schedule -v   # выборочно

ruff check .                            # линт
ruff format .                           # форматирование

# перед каждым коммитом — всё зелёное:
ruff check . && ruff format --check . && pytest
```

Окружение: Windows 10, Python 3.14 локально (CI — 3.11, минимальная версия по ТЗ), Docker Desktop,
авторизованный `gh`. В Git Bash `&&` работает; в PowerShell 5.1 — запускать команды по очереди.

## Git

- **Ветка на каждую фичу** (`feat/<slug>`, `fix/<slug>`); в `main` попадает только отревьюенный
  и согласованный код — через Pull Request, который я сам сливаю (шаги 5 и 9 цикла). Нужен авторизованный
  GitHub CLI (`gh auth status`). Напрямую в `main` коммитятся только правки правил работы
  (`CLAUDE.md`, скиллы).
- Все коммиты — по скиллу [`.agents/skills/git-commit/SKILL.md`](.agents/skills/git-commit/SKILL.md)
  (правила этого файла имеют приоритет, если противоречат скиллу).
- **Каждое логическое изменение — отдельный коммит**, ничего не копим. Перед коммитом проверки зелёные.
- Conventional Commits: `feat:`, `fix:`, `test:`, `refactor:`, `chore:`, `docs:`, `build:`, `ci:`.
  Описание со строчной буквы, без точки в конце, строки тела ≤ 100 символов. Scope — модуль или фича:
  `feat(pricing):`, `fix(webhooks):`, `test(payments):`.
- Хуки не обходить (`--no-verify` запрещён); упал хук — исправить причину и сделать новый коммит.
- После каждого коммита — `git push` текущей ветки. Force-push в `main` запрещён.
- Секреты (`.env`, `WEBHOOK_SECRET`) и локальная БД (`*.db`) в репозиторий не попадают — только
  `.env.example` с плейсхолдерами.
- Коммиты подписываются строкой `Co-Authored-By: <модель, которая писала код> <noreply@anthropic.com>`.

## Соглашения по коду

**Деньги — главное правило проекта**

- Все суммы — `int` в копейках: в моделях (`Mapped[int]`), схемах, ответах API и тестах. **`float` и
  `Decimal` для денег запрещены**, деление — только `//` и `divmod`.
- Скидка: `price * percent // 100`. График: `divmod(amount, months)`, лишние копейки — в первые платежи,
  `sum(schedule) == amount` всегда.

**Структура и слои**

- **Router** (`app/routers/`) — только HTTP: схемы запроса/ответа, коды, заголовки. Не содержит
  бизнес-логики и прямых запросов к БД сложнее «вызвать сервис».
- **Service** (`app/services/`) — бизнес-правила и транзакции. Не импортирует FastAPI (`HTTPException`,
  `Request`), а бросает доменные исключения из `app/errors.py`; в HTTP-коды их превращают обработчики в
  `main.py`.
- `app/services/pricing.py` — чистые функции без БД и FastAPI.
- ORM-модель наружу не отдаётся «как есть» — ответ всегда через Pydantic-схему (`response_model`).

**Типы и валидация**

- Аннотации типов везде; SQLAlchemy 2.0 стиль (`Mapped[...]`, `mapped_column`).
- Перечислимые значения (`method`, `status`) — `StrEnum`, общие для модели и схемы.
- Валидация входа — средствами Pydantic (`EmailStr`, `Literal[3, 6, 12]`, `model_validator`); ошибки
  валидации — стандартный 422 FastAPI, свой формат не нужен (ТЗ).
- Форматы ошибок, заданные ТЗ, соблюдаются буквально: 409 → `{"error": "invalid_transition"}`
  (через свой обработчик, не `HTTPException`, иначе будет `{"detail": ...}`).

**Надёжность**

- Инварианты держит БД, а не только код: `UNIQUE` на `idempotency_key`, условный `UPDATE ... WHERE
  status = :old` для смены статуса.
- Время — `datetime.now(UTC)`, timezone-aware.
- Секреты сравниваются через `hmac.compare_digest`, подпись считается от сырых байтов тела запроса.
